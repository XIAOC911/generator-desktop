# Fan Generator Desktop 开发源码文档

## 1. 项目定位

Fan Generator Desktop 是一个面向电商主图生产的桌面应用。当前代码已经把以下能力串成一条工作流：

1. 素材导入
2. 抠图
3. 固定排版 / 自由排版 / 模板套用
4. AI 文案、看图建议、场景图生成
5. 批量导出
6. 项目保存与恢复
7. 场景轮播图模板导出

这份源码的设计目标不是“一次性脚本”，而是“后续可以持续加功能”的可维护工程。

## 3. 分层架构

### 3.1 Electron 层

位置：`electron/`

职责：
- 本地文件系统访问
- 目录选择、文件保存、项目打开
- 抠图 Provider 调用
- 大模型请求代理
- 配置和敏感信息保存

主要文件：
- `electron/main.ts`：注册窗口和 IPC
- `electron/preload.ts`：向前端暴露 `window.fanDesktop.*`
- `electron/ipc/*.ts`：按能力拆分 IPC
- `electron/services/*.ts`：主进程内部服务

### 3.2 React UI 层

位置：`src/components/`

职责：
- 面板 UI
- 画布 UI
- 顶栏和工作区布局
- 与 store 和 service 交互

主要文件：
- `layout/Topbar.tsx`
- `layout/Sidebar.tsx`
- `canvas/CanvasStage.tsx`
- `panels/*.tsx`

### 3.3 业务层

位置：`src/services/` + `src/core/engines/` + `src/core/renderer/`

职责：
- 具体业务动作
- 排版算法
- 画布真实渲染
- 模板保存和读取
- 导出任务构建
- AI / 抠图 / 场景图工作流

### 3.4 数据模型层

位置：`src/core/models/`

职责：
- 统一定义项目数据结构
- 明确各模块的输入输出
- 降低功能扩展时的耦合

## 4. 当前最关键的数据结构

### 4.1 AppState

位置：`src/core/models/project.ts`

`AppState` 是前端运行时的总状态，包含：
- 画布
- 排版模式
- 商品素材
- 图层
- 记忆模板
- 背景模板
- 场景轮播模板
- 当前背景轮换
- 项目信息

后续新功能优先考虑“是否应该进入 AppState”。

适合进入 `AppState` 的数据：
- 会影响画布渲染
- 会被项目保存
- 会被模板复用
- 会被导出使用

不适合直接塞进 `AppState` 的数据：
- 纯 UI 临时开关
- 短生命周期请求状态（可放组件局部状态）
- 大体积二进制内容（应存文件路径或 dataUrl 引用）

### 4.2 Layer

位置：`src/core/models/layer.ts`

当前支持：
- `image`
- `text`

以后要加新图层类型，例如：
- sticker
- shape
- guide-line
- badge

推荐方式：
1. 在 `layer.ts` 新增联合类型
2. 在 renderer 中补绘制逻辑
3. 在交互命中检测中补支持
4. 在 LayerPanel 中补属性编辑

### 4.3 模板数据

位置：`src/core/models/template.ts`

当前有三类：
- `MemoryTemplate`：单场景记忆模板
- `BackgroundTemplate`：背景轮换模板
- `SceneCarouselTemplate`：整套场景轮播图模板

## 5. 核心模块说明

### 5.1 状态中心：`src/app/store/editorStore.ts`

这是项目最重要的单点状态入口。

职责：
- 保存全局 `AppState`
- 提供增删改查方法
- 控制 dirty 状态
- 在抠图结果回填时同步更新同源图层
- 驱动项目保存和恢复

开发原则：
- 所有“会影响项目内容”的修改，尽量通过 store 方法进入
- 不要在多个组件里直接拼装同样的状态更新逻辑
- 如果一个能力会同时影响 `sourceAssets` 和 `layers`，优先收口到 store

示例：新增“滤镜预设”功能时，建议加：
- `applyFilterPreset(layerId, preset)`
- `applyFilterPresetToSelectedAssets(preset)`

而不是在多个组件里各自 `map` 一遍 state。

### 5.2 画布渲染：`src/core/renderer/`

核心入口：`canvas-renderer.ts`

职责：
- 根据 `AppState` 画出当前画布
- 组合背景、固定排版、图层、文字

拆分建议：
- 背景逻辑放 `background-renderer.ts`
- 图片逻辑放 `image-renderer.ts`
- 文字逻辑放 `text-renderer.ts`
- 交互高亮和命中逻辑放 `interaction.ts`

开发原则：
- renderer 尽量只负责“画”，不要夹业务判断
- 如果某个布局规则可复用，先放 engine，再让 renderer 消费结果

### 5.3 排版算法：`src/core/engines/`

#### `free-layout-engine.ts`
负责随机自由排版。

#### `queue-engine.ts`
负责组合排版、单款排版和批量队列。

#### `copy-layout-engine.ts`
负责 AI 文案自动摆放。

#### `scene-placement-engine.ts`
负责场景图的商品落位。

开发原则：
- 排版规则优先写成纯函数
- 让输入输出尽量可测试
- 避免直接依赖 DOM

### 5.4 模板系统：`src/services/template.service.ts`

职责：
- 保存和读取模板集合
- 统一处理记忆模板 / 背景模板 / 场景轮播模板

相关扩展服务：
- `scene-template.service.ts`
- `scene-carousel-template.service.ts`

如果以后新增第四类模板，例如“文案模板”，也建议沿用同样做法：
- 模型定义进 `template.ts`
- 读写统一挂进 `template.service.ts`
- 单独业务操作拆到独立 service

### 5.5 导出系统：`src/services/export.service.ts`

职责：
- 构建导出任务
- 真实渲染到图片
- 支持自由排版、固定排版、背景变体、场景轮播模板导出

后续如果要加：
- 导出 PNG / JPG / WebP
- 导出 1:1、4:5、16:9 多尺寸
- 导出命名规则模板

建议直接扩在这里，而不是在面板里直接写导出流程。

### 5.6 项目系统：`src/services/project.service.ts`

职责：
- 新建 / 打开 / 保存 / 另存为
- 最近项目
- 自动保存
- 启动恢复

开发原则：
- 所有项目文件格式变更都要改 `version`
- 新增字段时优先考虑向后兼容
- `normalizeLoadedState()` 负责旧项目兼容非常关键

### 5.7 抠图系统：`src/services/matting.service.ts`

职责：
- 调主进程执行 Provider
- 批量抠图
- 重抠
- 把结果回填到素材和同源图层

当前 Provider：
- `edge-floodfill`：快速去底
- `rembg-python`：高精度去底

后续要加新 Provider 时，推荐步骤：
1. 在 `src/core/models/matting.ts` 增加参数模型
2. 在 `electron/ipc/matting.ipc.ts` 增加 Provider 分支
3. 在前端 MattingPanel 补表单
4. 保持前端调用入口不变

### 5.8 大模型系统：`src/services/llm.service.ts`

职责：
- 文案生成
- 看图建议
- 场景图生成
- 场景图复刻

主进程对应：`electron/ipc/llm.ipc.ts`

当前支持：
- OpenAI
- OpenAI-compatible
- Ollama

后续扩展建议：
- 对话模型和出图模型继续分离
- 如果引入工作流类 AI，新增 `taskType`，不要把所有提示词揉成一个大函数
- 提示词建议做模板化拆分，避免 `llm.service.ts` 继续膨胀

## 6. 典型功能从哪里入手开发

### 6.1 新增一个右侧功能面板

建议步骤：
1. 在 `src/components/panels/` 新建面板组件
2. 在 `Sidebar.tsx` 中接入
3. 如果需要全局状态，补到 `editorStore.ts`
4. 如果需要项目保存，补 `AppState`
5. 如果需要导出/模板/AI联动，再补 service

### 6.2 新增一个本地能力（例如 OCR、本地图像处理）

建议步骤：
1. 前端只放参数和结果展示
2. 具体执行逻辑放 Electron 主进程 IPC
3. 如果依赖系统环境，增加环境检测按钮和提示
4. 敏感路径或命令只放主进程，不要放前端

### 6.3 新增一个 AI 能力

建议步骤：
1. 先判断是文本、视觉、还是图像生成
2. 在 `llm.service.ts` 增一个明确入口，如 `generateXxx()`
3. 在 `electron/ipc/llm.ipc.ts` 增对应调用链
4. 在 UI 面板中增加配置和结果区
5. 如果结果会回写画布，优先走 store/service，不要组件直接改 layers

## 7. 后续开发建议规范

### 7.1 不要把业务直接写回组件

推荐：
- 组件负责收集参数和展示结果
- service 负责业务动作
- store 负责状态写入

### 7.2 会被保存的功能，一定先考虑项目兼容性

任何新增字段都要考虑：
- 新项目怎么写
- 老项目怎么读
- 自动保存怎么恢复

### 7.3 新增模板能力时，不要重复造轮子

优先复用：
- `template.service.ts`
- `scene-carousel-template.service.ts`
- `project.service.ts`

### 7.4 渲染与业务分离

例如：
- “应该把标题放哪里”是业务/engine
- “把文字画出来”是 renderer

不要把两者混在一起。

### 7.5 命名和职责要收口

如果以后继续加功能，优先遵循：
- `core/models`：数据模型
- `core/engines`：纯算法与布局
- `core/renderer`：画图
- `services`：业务流程
- `components`：UI
- `electron/ipc`：主进程能力入口

## 9. Windows 打包建议

当前环境里无法直接产出可安装 EXE，原因是：
- Electron 安装阶段需要从 GitHub 下载二进制
- 当前容器网络无法访问该下载地址
- 当前容器也没有 Windows 打包所需的 Wine / NSIS 工具链

所以正确做法是：
1. 在 Windows 电脑上打开本项目
2. 执行 `npm install`
3. 执行 `npm run dist:win`
4. 生成 NSIS 安装包

详细命令见：
- `docs/03-Windows安装包打包说明.md`
- `tools/build-win-installer.ps1`
- `tools/build-win-installer.bat`
